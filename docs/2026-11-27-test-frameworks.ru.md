# Можно ли запускать пары Measure внутри mcp-assert или mcp-test-harness?

*English version: [2026-11-27-test-frameworks.md](2026-11-27-test-frameworks.md)*

Написано Claude (ИИ) 27 ноября 2026 года, в утренней сессии по расписанию. Заметка о предшественниках от 24 ноября ([`2026-11-24-new-checks-prior-art.ru.md`](2026-11-24-new-checks-prior-art.ru.md)) решила не писать собственный набор для тестирования, потому что уже есть два фреймворка для проверки серверов для ИИ-агентов, и оставила один вопрос открытым: можно ли отдать эталонные пары Measure в таком виде, чтобы их запускал один из этих фреймворков и автор сервера проверял свой сервер одной командой? Сначала нужно было выяснить две вещи: можно ли сравнить число с допуском и можно ли записать «инструмент должен отказать». Эта заметка отвечает на оба вопроса.

Вторая ссылка оказалась не тем, что ожидала заметка 24 ноября. `mcp-test-suite` — не собрание наборов тестов для каких-то областей, а набор связок (общий YAML-файл, адаптеры для Node, Java, Go и .NET, GitHub Action), чтобы запускать harness из других языков. Эталонных вопросов в нём нет.

## Два вопроса

**1. Число с допуском: нет, ни в одном из фреймворков в декларативной форме.**

- mcp-assert: проверки результата — `equals` (точное совпадение текста без пробелов по краям), `contains`, `not_contains`, `matches_regex`, `in_order` и `json_path`. В `checker.go` проверка `json_path` превращает ожидаемое и полученное значения в текст и сравнивает строки. Допуска нет, числового сравнения нет, кроме особого поля `net_delta`.
- mcp-test-suite: у случая есть ожидаемое содержимое `expected`; и учебник, и код сравнивают его на равенство.
- mcp-test-harness: `assert_tool_call(session, tool, arguments, expected)` сериализует ответ и сравнивает с `expected` на равенство.

Допуски Measure малы (`1e-12` относительных для точных ответов, `1e-9` для округлённых; [`FORMAT.md`](../FORMAT.md)), но не нулевые: они нужны потому, что инструменты считают в двойной точности, и инструмент, ошибившийся в последнем двоичном разряде, не ошибся. Точное сравнение такой инструмент «провалит». Регулярным выражением можно изобразить допуск для одного числа, записанного одним способом, но не для любого значения в любой записи, и эталон спрятался бы в шаблон, который никто не прочтёт.

Harness умеет запускать и тесты на Python, где можно сравнивать как угодно. Но тест на Python для конкретного сервера — это ровно то, чем уже являются адаптеры Measure.

**2. «Должен отказать»: да, в обоих, но уже, чем в Measure.**

- mcp-assert: `is_error: true` проходит, если инструмент ставит флаг протокола `isError`.
- mcp-test-suite: `expect_error` принимает `true`, часть текста сообщения или код; в коде сказано, что сбой самой тестовой машинерии не должен засчитываться как ожидаемая ошибка, и это правильная осторожность.

Measure решает, отказ ли это, в каждом адаптере, по тому, что сервер на самом деле вернул. Большинство серверов отказывают через `isError`, для них это перенеслось бы. Не перенеслось бы для инструмента, который отказывает обычным текстом, и для того, кто ставит `isError` из-за собственной поломки: фреймворк их не различит, а адаптеры Measure различают (см. `bench/adapters/unit_converter_mcp.py`, где отказом считаются только два вида сообщений, а всё остальное записывается как ошибка сервера).

## Препятствие покрупнее: каждый сервер говорит на своём языке

Даже с допуском пару нельзя записать один раз и запускать против любого сервера. Пара «переведи 1 дюйм в миллиметры» для unit-converter-mcp превращается в вызов инструмента `convert_length` с аргументами `value`, `from_unit: "inch"`, `to_unit: "millimeter"`, а ответ берётся из поля `converted_value`. У каждого другого сервера своё имя инструмента, свои имена аргументов, своё написание единиц и своя форма ответа. Этот перевод и делают адаптеры Measure. Выгрузка для фреймворков была бы отдельным файлом на каждый сервер, построенным из таблиц адаптера, то есть повторением адаптера в более слабом виде.

## Решение

- **Пары для этих фреймворков сейчас не выгружаем.** С точным сравнением выгрузка провалила бы правильные инструменты и создала бы второй набор вердиктов рядом с собственным, которые могли бы расходиться.
- **Автору сервера, который хочет проверить свой сервер, по-прежнему проще всего сам Measure:** адаптер (большинство короче 150 строк) и `python3 -m bench <инструмент>`. Короткое руководство для авторов о том, как написать адаптер, помогло бы им больше, чем выгрузка. Не начато; в плане этого нет, здесь записано как кандидат.
- **Возможный вклад, никому не предложенный:** числовое сравнение с допуском для `json_path` в mcp-assert сделало бы выгрузку осмысленной. 27 ноября в его трекере не было ни одного issue со словами «tolerance», «numeric», «float» или «approximate» (поиск GitHub; в трекере harness тоже нет ни одного со словами «tolerance», «numeric», «approx»). Написать авторам — значит публиковать вне лаборатории, на это нужно «да» владельца; сейчас это не нужно, потому что Measure без этого обходится.
- Оба фреймворка умеют повторить вызов и сравнить результаты (`--trials` у mcp-assert, проверка повторного вызова у harness). Второй прогон каждого инструмента в раунде (решено 25 ноября) — та же мысль; брать у них нечего, кроме того, чтобы назвать их соседями.

## Что не получилось

Попытку установить mcp-assert 0.12.3 и unit-converter-mcp 0.1.2 во временное окружение, чтобы прогнать одну пару через mcp-assert, отклонила проверка разрешений сессии. Повторять или обходить её не стал. Поэтому ничего выше не наблюдалось при запуске фреймворков; каждое утверждение взято из исходного кода и документации на коммитах, названных в таблице.
